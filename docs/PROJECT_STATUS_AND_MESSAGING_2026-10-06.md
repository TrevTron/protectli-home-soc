## The investigation correction

The frozen first broader run remains a failure: zero of 18 measured decisions passed and all 24 prose reviews reached their 700-token cap. Its full membership and hashes are preserved. Passing the existing constrained analyst validator did not imply passing an investigation task.

Development found that the original schema was supplied to the decoder without a complete task contract in the model's trusted instructions. Explicit field meanings alone improved some decisions but still produced contradictions. Natural JSON alone omitted required fields. Those failed attempts remain separate. These observations do not isolate a single universal model or decoder defect.

The new contract places the full schema and semantics in the system prompt. Fixed boolean slots give every decision, context code and read-only check one place, eliminating duplicate decision-code entries structurally. Model-authored observations, counts and citations still face independent source checks. Boolean slots are reversibly converted to the original decision-list representation, without supplying correct values or repairing wrong observations.

The full correction also found actual input truncation. In V5, expanded mixed-case prompts of 5,107 and 5,464 tokens were cut to 2,050, invalidating the A/B/C comparison. V6 changed only investigator context from 4,096 to 8,192 and required runtime proof of complete input. All 18 measured and six practice investigator answers passed. All 56 scheduled requests completed with full-context and GPU evidence; no investigator or reviewer output reached the unchanged 700-token cap. The original failed run and intermediate failures remain unchanged.

The distinct-weight reviewer returns a compact defect checklist instead of an essay. It completed all 24 reviews, but only 18 checklists matched the independent categories. It falsely flagged missing checks on all six empty-case answers, even when the visibility check was present. It passed only one of six deliberately corrupted-answer controls, missing incorrect counts, duplicates and omitted decisions. A separate reasoning-mode trial capped without a final answer. This reviewer cannot certify findings and is not deployed. All three investigator conditions passed, so this exposed regression does not establish an assistance or grouping advantage, unseen incident accuracy or human usefulness.

## How it compares with TriageWall

The current [TriageWall README](https://github.com/aaronphifer/triagewall) documents a broader alert-triage application: Suricata and optional Wazuh, scoped deterministic noise policies, a local residual classifier, SQLite decision history, an investigation workbench, and versioned configuration with preview and rollback. Its [operations guide](https://github.com/aaronphifer/triagewall/blob/main/docs/operations.md) also documents verified backup and pruning controls. Those operational capabilities exceed this project's current implementation in those areas.

Our contribution is the reproducible Protectli/OPNsense build and its packet-to-evidence path: actual appliance configuration, thermal observations, owned-client block/rollback, original record hashes, separately recorded endpoint context, review notes, restart and citation-restoration checks. Local models, SQLite, evidence review and GPU inference are shared approaches, not novelty claims. Our first noise reduction collapses repetition without suppressing records. TriageWall's policies classify expected activity before residual model review.

No matched cross-project workload has been executed, so there is no accuracy, speed or usability winner. Its published evaluation metrics and our constrained-delivery or investigation-regression scores describe different tasks. TriageWall currently identifies its license as AGPL-3.0; its code was not copied here. The earlier CPU-only comparison is historical and no longer describes our current GPU deployment.
